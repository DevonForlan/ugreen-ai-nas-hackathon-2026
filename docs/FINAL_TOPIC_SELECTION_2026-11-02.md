## 4. Exactly three finalist definitions

### F1 — ArchiveRescue: companion-aware NAS archive intake

**Problem:** Repeated shoot/legacy intake can treat an already archived source as redundant while overlooking a new edit companion or same-name different capture.
**Solution:** Review a bounded staged batch against selected archive folders, preserve human-approved source/companion units, perform new-copy actions and verify the copied bytes.

**Trigger:** After the user/platform has already staged a shoot or old-drive folder on NAS, before admitting it into the shared archive. **Inputs:** exact allowed staging/archive roots; a small explicit inventory; readable notes/XMP where available; JPEG previews; source media as opaque bytes if native decoding is unsupported; approved new destination. Existing managed catalogs are outside scope: do not rename/move their referenced originals or promise catalog relinking.

**Workflow:** enumerate → tool hashes/stat → optional image/document interpretation and companion hypotheses → human resolves file-family/preserve/skip choices → preview exact paths and gateway approvals → copy approved files into a fresh source-relative bundle directory → rehash source/destination and expose partial results → save/read back the approved intake record. No deletion, moving sources, overwriting existing files, flattening ambiguous names, automated dependency discovery or disk-erasure advice.

**Saved output:** actual new folder containing the confirmed files, plus intake record containing source roots/paths, observed hashes, proposed versus confirmed relationships, skipped copies, exceptions and per-copy verification. This is neither ASC MHL interoperability nor an immutable preservation system. “Verified” means byte comparison within inspected scope, not decode validity, authentic capture, working edits, backup success or permission to erase the old drive.

**Strongest incumbent:** PhotoPrism for import/duplicate/related-file grouping; OffShoot is the stronger verified-transfer control [S06–S08]. Both may be better for configured users. Our hypothesized difference is a small, conversational, pre-approved admission across existing NAS folders without adopting another media catalog; uniqueness and net effort improvement are unmeasured.

**General-AI substitution:** HIGH with authorized filesystem/hash/copy tools. **Hackathon collision:** HIGH (dedupe/organizer family). Only the visible exception—intentionally retaining duplicated source bytes to preserve a distinct approved edit unit—and executed verified copy justify keeping it above generic cleanup. A standalone prompt/table cannot deliver the byte-level filesystem result; a general agent with the same tools can. There is no algorithmic moat.

**Demo:** 180 seconds, nine planned assets (section 9L), one source/sidecar unit copied, a same-name different-file exception and human confirmation. **Single kill gate:** official source/destination SHA-256 and non-overwriting copy cannot be obtained reliably for the tiny batch; a report-only fallback is not this topic.

### F2 — ConditionReturn: loan-return packet preflight

**Problem:** A returned object's documentation can appear complete while containing a different object's report or lacking a lender-required photo view.
**Solution:** Produce a narrowly scoped object/view reconciliation for a registrar, preserving unresolved condition statements for a conservator.

**Trigger:** Return packet arrives before record acceptance. **Inputs, eight planned assets:** `scope.txt`, `loan-object-list.pdf`, `outgoing-report.pdf`, `return-report.pdf`, `front.jpg`, `reverse.jpg`, `decoy-label.jpg`, `lender-appendix.pdf` (unread fixture). The allowed packet and view checklist are human-specified, not guessed from typical museum practice.

**Workflow:** enumerate; extract supplied object/loan/date IDs; read image labels/view descriptions; compare the reports/checklist; show wrong-object exception, a clean agreed view and unread-dependent uncertainty; registrar defers the disputed record; save a new preflight note. Human decides actual condition, damage and acceptance. Never change the CMS, enforce rights, annotate rendered damage or assign liability.

**Exact expert requirements:** file-agent enumeration/cat; document-agent extract/qa/reconcile; photo-agent vision-ocr/vision-vlm/meta; knowledge-agent save-text. Format/locator fallback: legible text-equivalent loan/checklist records are valid if already supplied as authoritative inputs; returned image labels may be manually confirmed. No simulated OCR output or fabricated page link. If source identity cannot be established, mark unresolved; if core cross-record linkage fails, stop.

**Strongest incumbent:** Articheck plus EMu [S14–S15]. Their histories, multimedia and reporting already solve the standard job; only external/legacy packets outside correct integration are a plausible segment, not a proven missing feature. **General-AI substitution:** HIGH. **Collision:** MEDIUM exact loan-return story, HIGH generic evidence/inspection mechanism. NAS advantage is conditional persistent collection-media access; not exclusive to NAS.

**Demo, 170 seconds:** 0–20 explain return; 20–60 current loan versus decoy ID; 60–110 inspect actual front/reverse references and one missing declared view, with clean control; 110–140 unread appendix prevents completeness; 140–170 registrar defers and approves note saving. Do not call an unread file missing or diagnose a scratch from VLM. **Single kill gate:** competent Articheck/EMu plus same-folder AI leaves no meaningful review benefit. This uncertainty is reflected in its low differentiation score, not hidden by the museum setting.

### F3 — SampleTrail: field-to-lab document correspondence

**Problem:** An alias correction or wrong label can look like a missing/duplicate sample while a legitimate QA duplicate must remain distinct.
**Solution:** Reconcile one provided plan/label/custody/receipt packet for a custodian without certifying custody or touching lab systems.

**Trigger:** Receipt/custody records arrive before human documentary acceptance. **Inputs, eight planned assets:** `scope.txt`, `sampling-plan.pdf`, `field-log.txt`, `labels.jpg`, `custody-v1.pdf`, `custody-amendment.pdf`, `lab-receipt.pdf`, `qa-key.txt`. The QA key explicitly defines intentional duplicates; no signature validation inferred.

**Workflow:** inventory; extract declared IDs; OCR label image; apply supplied dated amendment/alias policy; keep legitimate QA duplicate; flag wrong label versus receipt; custodian resolves/defer; save a new correspondence note with actual source pointers. A dirty or unread label must remain uncertain, never normalized to the nearest expected ID.

**Exact expert requirements:** same file/document/photo/save classes as F2, no audio or instrument parser. If document format extraction fails, an already supplied readable approved text export is an admissible fallback; the raw failed input stays listed. Cannot replace label correspondence with a hand-entered answer. Native LIMS, eCoC submission, electronic signature, calibration, contamination/safety assessment and analytical-result validation are excluded.

**Strongest incumbent:** ESdat, with EarthSoft EDGE/EQuIS as another substantial field/custody control [S19–S20]. Unified deployments already match plans and lab information; unmanaged cross-vendor exports are only a hypothesized residual. **General-AI substitution:** HIGH; **collision:** MEDIUM exact QA/alias story, HIGH generic checklist assistant. LAN record architecture is direct evidence; a UGREEN NAS buyer cohort is UNKNOWN.

**Demo, 175 seconds:** 0–20 distinguish the real QA duplicate; 20–65 read plan/QA key; 65–115 compare amended identity and wrong label; 115–145 show clean correspondence and uncertain OCR; 145–175 custodian refuses unsupported acceptance and saves note. **Single kill gate:** useful output requires actual managed-system custody validation/signatures rather than the bounded documentary comparison. No conceptual expansion to regulatory certification.

## 9. FINAL SELECTED TOPIC

### A. Final working name

**ArchiveRescue** — companion-aware NAS archive intake. Track recommendation: **Unleash Your Creativity** (supported media selection/organization), not a recovery product.

### B. Positioning — 15 words or fewer

**Preserve creative file bundles while safely admitting staged media into an existing NAS archive.**

14 English words. “Safely” here means explicit scope, no source modification, human-approved new copies and observed byte checks, not a security/recovery guarantee.

### C. Exact target user

An independent photographer or 2–5-person photo studio already keeping original shoots and edit companions on a shared NAS, receiving unmanaged folders from old drives or collaborators. Exclude cloud-only albums, broken disks, properly managed live Lightroom catalogs requiring relinking, and users whose configured importer already solves the job comfortably.

### D. Exact trigger

User manually invokes the Skill after the new source folders are **already accessible in NAS staging**, before copying selected creative units into the long-term archive. No mount, watch, scheduled run or remote source fetch.

### E. Exact inputs

User-approved staging root(s), selected archive comparison root(s), bounded file inventory, readable shoot notes/companion files where available, JPEG previews, source-media bytes and a genuinely new destination. An explicit companion naming rule/user confirmation binds opaque source formats; the Skill never claims RAW decoding or edit rendering. Initial operational scope: one small batch, approximately 10–20 files; the demo uses nine. No full-library indexing or TB throughput promised.

### F. Exact workflow — eight user-visible steps

1. Confirm allowed staging/archive roots, bounded inventory, companion rules and fresh output location.
2. Show returned file list and read failures; obtain actual per-file hashes/stat for compared candidates.
3. Propose shoot/file families from readable notes, JPEG observations and naming context; distinguish observations from uncertain relationships.
4. Show byte-equal source copies separately from new companion/edit units and same-name different captures; require the human's preserve/skip decisions.
5. Preview exact source-to-new-destination paths and any intentional byte duplication needed to preserve a functional bundle; request platform write approvals.
6. Copy only the confirmed small unit, preserving its basename/relative layout, with overwrite disabled; leave all sources and existing archive files untouched.
7. Re-read actual source/destination hashes and copy outcomes; label partial/unverified results honestly, without claiming transaction or automatic rollback.
8. Approve and save/read back a new intake record next to the output, recording confirmed relationships, actual paths/hashes, skips and exceptions.

### G. Exact output

A real new archive bundle and an inspected intake record; the record is secondary to the files. Same bytes may intentionally be present twice if different edit companions require distinct intact units. No “space saved” promise, deletion offer, recovery certificate, standards-compliant MHL, immutable audit log or functioning-catalog claim.

### H. Human decision

Confirm ambiguous relationships, whether the alternate companion should be retained, which duplicate copy is unnecessary **for this admission**, and exact new destination. Approve the write actions and unresolved-result wording. Approval is not permission to erase original drives or proof of copyright/ownership.

### I. Why NAS

The existing growing media archive is necessary input state and the destination of the actual operation. Original captures, alternate edit instructions and historical project folders are reused across batches and, for a studio, across workstations. Running the approved copy/check chain through the archive's native experts can avoid maintaining another media-catalog installation merely to admit a small batch. An equivalent shared server or capable agent mounting the same NAS can reproduce this architecture; the advantage is practical integration with an existing data home, not an exclusive NAS protocol or unmeasured transfer saving.

### J. Why not ChatGPT

ChatGPT can understand the relationships and, with authorized filesystem tools, can hash and copy the same files [S26]; Claude has local-file tools too [S27]. We choose a bounded UGREEN-native workflow because its intended deliverable is a human-approved storage change with genuine per-file verification, through registered expert actions, rather than advisory prose. This is a product interaction/integration choice without a reasoning moat. If the same-folder agent or configured importer provides the same result with equal preparation and review work, the claimed convenience advantage disappears; no upload-limit or inability argument is used.

### K. Why now / why UGREEN

UGREEN already positions AI around local search, albums and file organization [S10]. The contest's official surface additionally exposes hashes and approved copies [S03], allowing an entry to show how an AI suggestion becomes a checkable file outcome. This is a more honest use of the kit than promising unsupported background/backup infrastructure. Current native-feature overlap remains high, so the submission must lead with the companion exception and executed result, not “AI photo organizer.”
